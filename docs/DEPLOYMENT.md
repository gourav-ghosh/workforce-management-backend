# Production Deployment on an Ubuntu VPS

This guide deploys the backend to a generic Ubuntu VPS, including Hostinger. It uses Docker Compose, PostgreSQL, Gunicorn, and two Nginx layers:

```text
Internet -> Hostinger/VPS Nginx (HTTPS) -> bundled Nginx (127.0.0.1:8080)
         -> Gunicorn/Django (container network) -> PostgreSQL
```

The bundled Nginx serves collected static files and uploaded media from Docker volumes. The VPS-host Nginx terminates TLS and forwards requests to it on loopback.

## 1. Prerequisites

- Ubuntu 22.04 or 24.04 VPS
- A domain or subdomain, for example `api.example.com`
- DNS A record pointing the domain to the VPS public IPv4 address
- SSH access with sudo privileges
- Docker Engine and Docker Compose v2
- Ports `80/tcp` and `443/tcp` open in the VPS firewall and Hostinger cloud firewall

Install Docker and Compose. Package names vary slightly by Ubuntu release:

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-plugin ca-certificates curl
sudo systemctl enable --now docker
docker compose version
```

If `docker-compose-plugin` is unavailable, install the distribution's `docker-compose-v2` package and rerun `docker compose version`.

Open the required ports without locking yourself out of SSH:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
```

## 2. Prepare the application

### 2a. How the database connection is resolved

`config/settings/base.py` picks the database in this order, using the first
option that is present:

1. **`DATABASE_URL`** — a single connection URL. This is what Docker Compose,
   Railway, Render, Heroku and most PaaS providers inject, and it always wins.
2. **Discrete `POSTGRES_*` / `DB_*` / `PG*` variables** — assembled into a
   URL. `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` are the names
   used by `docker-compose.prod.yml`; `DB_HOST`/`DB_PORT` let you point at a
   PostgreSQL server outside the Compose network.
3. **SQLite** — a last-resort local fallback so a fresh checkout still runs
   without PostgreSQL. Never rely on this in production.

A `postgres://` scheme is rewritten to `postgresql://`, and credentials
containing `@`, `:` or `/` are URL-encoded, so passwords generated by
`openssl rand` are safe to use. Set `DATABASE_SSLMODE=require` when the
managed database needs TLS.

**What is the database host in production?** It depends on where the database
runs, and the same value works whether you set `DATABASE_URL` or the discrete
variables:

| Topology | Host to use |
| --- | --- |
| PostgreSQL in the same Compose project (this guide) | `db` — the Compose service name; `docker-compose.prod.yml` builds the URL for you |
| Managed PostgreSQL (Railway, Render, Neon, Supabase, RDS…) | the hostname the provider gives you, e.g. `pg.railway.app` or `ep-xxx.aws.compute.rds.amazonaws.com` |
| PostgreSQL on the same VPS, outside Compose | `127.0.0.1` |
| PostgreSQL on a different machine | that machine's IP or DNS name |

Do not hard-code a host in the image. Set it as an environment variable so
the same image runs in every environment.

### 2b. Prepare the application

Copy the backend repository to the VPS, for example under `/opt/workforce-management-backend`, and enter its directory:

```bash
cd /opt/workforce-management-backend
cp .env.example .env
chmod 600 .env
```

Generate a secret and database password locally or on the server:

```bash
openssl rand -base64 48
openssl rand -hex 32
```

Keep `EMAIL_BACKEND` and the SMTP settings consistent with your provider. For
example, a Hostinger SMTP account may use port `465` with
`EMAIL_USE_TLS=False`, or port `587` with `EMAIL_USE_TLS=True`; confirm the
values shown by Hostinger. The password-reset email is required for the
account-based reset flow. Workers without an email address must use an admin
password reset instead.

Set at least these values in `.env`:

```dotenv
DJANGO_SECRET_KEY=<long-random-secret>
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=api.example.com
PUBLIC_BASE_URL=https://api.example.com
CORS_ALLOWED_ORIGINS=https://app.example.com
POSTGRES_DB=workforce_management
POSTGRES_USER=workforce
POSTGRES_PASSWORD=<long-random-database-password>
SECURE_HSTS_SECONDS=0
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=<smtp-host>
EMAIL_PORT=587
EMAIL_HOST_USER=<smtp-user>
EMAIL_HOST_PASSWORD=<smtp-password>
EMAIL_USE_TLS=True
DEFAULT_FROM_EMAIL=no-reply@example.com
```

Use the exact public API host in `DJANGO_ALLOWED_HOSTS` and `PUBLIC_BASE_URL`. Set `CORS_ALLOWED_ORIGINS` to the web/mobile-web origin that calls the API; native mobile requests do not use browser CORS. Keep `SECURE_HSTS_SECONDS=0` until HTTPS is verified and you are ready to commit to HSTS. The SMTP values above are examples; use the exact host, port, and TLS mode supplied by your email provider.

Do not expose PostgreSQL or Django directly to the internet. The production Compose file exposes only the bundled Nginx service.

## 3. Deploy the application stack

Validate the Compose configuration and start the stack with the host-Nginx override:

```bash
docker compose \
  -f docker-compose.prod.yml \
  -f deployment/docker-compose.prod-host-nginx.yml \
  config

docker compose \
  -f docker-compose.prod.yml \
  -f deployment/docker-compose.prod-host-nginx.yml \
  up -d --build
```

The override publishes bundled Nginx only at `127.0.0.1:8080`. Django remains reachable only inside the Compose network. Validate the merged configuration with:

```bash
docker compose \
  -f docker-compose.prod.yml \
  -f deployment/docker-compose.prod-host-nginx.yml \
  config --quiet
```

Check the services:

```bash
docker compose \
  -f docker-compose.prod.yml \
  -f deployment/docker-compose.prod-host-nginx.yml \
  ps
```

The entrypoint waits for PostgreSQL, applies migrations, and collects static files before Gunicorn starts.

## 4. Configure HTTPS on the VPS

Install Nginx and Certbot:

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
```

Set the real API hostname in your shell before running the commands below:

```bash
export API_DOMAIN=api.example.com
```

Replace the placeholder HTTP server with a temporary HTTP-only block first, so
Nginx can start before certificate files exist:

```bash
sudo tee /etc/nginx/sites-available/workforce-api >/dev/null <<NGINX
server {
    listen 80;
    server_name ${API_DOMAIN};
    location /.well-known/acme-challenge/ { root /var/www/html; }
    location / { return 301 https://\$host\$request_uri; }
}
NGINX
sudo ln -sf /etc/nginx/sites-available/workforce-api /etc/nginx/sites-enabled/workforce-api
sudo nginx -t && sudo systemctl reload nginx
```

Obtain the certificate:

```bash
sudo certbot certonly --nginx -d "${API_DOMAIN}"
```

The template expects certificate files at:

```text
/etc/letsencrypt/live/<your-domain>/fullchain.pem
/etc/letsencrypt/live/<your-domain>/privkey.pem
```

After the certificate exists, install the checked-in host template, substitute
the placeholder domain, and reload:

```bash
sudo cp deployment/nginx-host.conf /etc/nginx/sites-available/workforce-api
sudo sed -i "s/api\.example\.com/${API_DOMAIN}/g" /etc/nginx/sites-available/workforce-api
sudo nginx -t
sudo systemctl reload nginx
```

Alternatively, run `sudo certbot --nginx -d "${API_DOMAIN}"` and let Certbot
issue and configure the certificate, then replace the generated block with the
checked-in template. If you manage certificates outside Certbot, place the
full-chain certificate and private key at the paths above and reload Nginx.

The host Nginx configuration:

- redirects HTTP to HTTPS;
- proxies to `http://127.0.0.1:8080`;
- forwards `X-Forwarded-Proto: https`, which Django production settings require;
- allows 20 MB uploads, matching the default `MAX_UPLOAD_SIZE_MB=10` with protocol overhead;
- leaves static and media serving to the bundled Nginx container.

## 5. Verify the deployment

From the VPS, verify the loopback path:

```bash
curl -i http://127.0.0.1:8080/api/health/
```

Verify public HTTPS after DNS and certificate setup:

```bash
curl -I https://api.example.com/api/health/
curl -s https://api.example.com/api/health/
```

Expected health response:

```json
{"status": "ok"}
```

Also test a redirect and inspect logs when troubleshooting:

```bash
curl -I http://api.example.com/api/health/
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml logs -f web nginx
```

## 6. Create an administrator

Create a Django superuser inside the web container:

```bash
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec web python manage.py createsuperuser \
  --mobile_number <mobile>
```

Django's `createsuperuser` command prompts for the password interactively; the
`--email` flag shown by some Django versions is not part of this custom user
model. If an email address is needed for password reset, set it after creating
the account from `/admin/` or with a small management shell. The custom user
manager automatically assigns the `ADMIN` application role. This account can access both `/admin/` and ADMIN-only API endpoints. A Django staff account without the `ADMIN` role cannot call ADMIN-only API endpoints.

## 7. Backups

Run backups from the backend directory. Store the resulting files outside the VPS, such as Hostinger object storage, another server, or an encrypted local backup location.

### PostgreSQL

Use the custom format so restores can select schemas or tables:

```bash
mkdir -p backups
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec -T db sh -c 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > "backups/db-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

### Uploaded media

```bash
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec -T web sh -c 'tar -czf - media' \
  > "backups/media-$(date -u +%Y%m%dT%H%M%SZ).tar.gz"
```

Schedule both commands, retain multiple generations, and test restores regularly. A database backup alone is incomplete because photos and documents live in the `media_prod` volume.

### Restore

Stop application writes before restoring. Restore the database into the existing production database:

```bash
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' \
  < backups/db-YYYYMMDDTHHMMSSZ.dump
```

Restore media:

```bash
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec -T web sh -c 'tar -xzf - -C /app' \
  < backups/media-YYYYMMDDTHHMMSSZ.tar.gz
```

Run migrations after a database restore and verify the application before reopening writes:

```bash
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec web python manage.py migrate --noinput
```

## 8. Updates and operations

For a normal release:

```bash
git pull
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  up -d --build
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec web python manage.py migrate --noinput
```

Useful commands:

```bash
# Follow logs
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml logs -f

# Restart services
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml restart

# Show container status
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml ps

# Run a management command
docker compose -f docker-compose.prod.yml -f deployment/docker-compose.prod-host-nginx.yml \
  exec web python manage.py <command>
```

## 9. Production security checklist

- `DJANGO_DEBUG=False`.
- `DJANGO_SECRET_KEY` is unique and high entropy.
- `DJANGO_ALLOWED_HOSTS` contains only the public API hostnames.
- `CORS_ALLOWED_ORIGINS` contains only trusted web origins.
- `PUBLIC_BASE_URL` is the HTTPS API origin.
- PostgreSQL credentials are unique and not committed.
- `.env`, backups, and certificate private keys are not publicly readable.
- VPS and Hostinger firewalls allow only SSH, HTTP, and HTTPS.
- TLS certificates renew automatically; check renewal with `sudo certbot renew --dry-run`.
- Database and media backups are offsite and restoration has been tested.
- HSTS is enabled only after HTTPS is stable.
- API `ADMIN` authorization and Django `/admin/` access are understood as separate controls.

## 10. Testing the deployment on a free/low-cost platform

The VPS + host-Nginx layout above is the right shape for production, but it is
not the only way to prove the stack works. These platforms run the same
Dockerfile, terminate TLS for you, and inject `DATABASE_URL` automatically:

| Platform | Database | Notes |
| --- | --- | --- |
| **Railway** | Railway PostgreSQL plugin | Best fit. Add the Postgres plugin, then a service from this repo's Dockerfile. Set `DJANGO_SETTINGS_MODULE=config.settings.production`, `DJANGO_DEBUG=False`, a strong `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `PUBLIC_BASE_URL`, and `DATABASE_SSLMODE=require`. |
| **Render** | Render PostgreSQL | Same variables; use the Dockerfile and set the health check path to `/api/health/`. |
| **Fly.io** | Fly Postgres | Same variables. |
| **PythonAnywhere** | own PostgreSQL | Manual WSGI/venv setup rather than Docker. |

Notes that apply to all of them:

- **Do not deploy `docker-compose.prod.yml`.** It expects a host Nginx on
  `127.0.0.1:8080` and publishes that port. On a PaaS, deploy only the `web`
  service; the platform routes HTTPS traffic straight to Gunicorn. The
  container already binds `0.0.0.0:${PORT:-8000}`, so the platform's `PORT`
  is honoured automatically.
- The entrypoint already runs `migrate` and `collectstatic` before Gunicorn
  starts, so no extra release command is required.
- Static files are served by WhiteNoise, so the Nginx container is not needed.
- **Media is ephemeral on most free tiers.** Uploaded photos live on the
  container filesystem and disappear on every redeploy. Mount a volume, or
  move uploads to object storage, before using this for real data.
- Free tiers sleep and have small instance sizes, so cold starts are slow.
  They are fine for validating the flow, not for real users.
- Keep `SECURE_SSL_REDIRECT=True`; the PaaS proxies send
  `X-Forwarded-Proto: https`, which production settings already trust.

To validate a free-tier deployment end to end, point the mobile app at the
public host:

```bash
# in the mobile repo
flutter test integration_test/live_api_test.dart -d emulator-5554 \
  --dart-define=API_BASE_URL=https://<your-app-domain>/api/v1
```
